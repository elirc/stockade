# Sol: initial Stockade design challenge

This is a local commerce simulator, so the strongest useful claim is inventory conservation under real process contention. `onHand` represents physical units; `reserved` is a subset of those units. Checkout increases `reserved`, shipping decreases both counters, and cancel/expiry/decline decreases only `reserved`. `available = onHand - reserved` must never be negative. Every state transition, ledger row, and activity row must commit in the same transaction. A read followed by a write in application code is insufficient when two server processes share one SQLite file.

The checkout key must be scoped to the authenticated tenant and saved with a fingerprint of the normalized item intent. Retrying the same key after a lost response must return the original order without consuming stock again, even after the order changes state. Reusing that key for a different intent must fail. Multi-line checkout must reserve all lines or none. Price and line totals come from the catalog, with integer overflow checked before writing.

The difficult transition race is expiry against payment or shipping. The database transaction must recheck state and expiry at the time of the transition, so an expired hold cannot later become paid. Repeated cancel, expiry, ship, and refund must not double-release or double-decrement. A failed activity insert should roll back the inventory change as well as the order. Tenant scoping must apply to individual order and product IDs, not only list queries.

The proposed two-process load proof is 500 unique one-unit checkout keys against 100 available units, split across two Node servers using the same database file. Acceptance is exactly 100 created orders, 400 sold-out conflicts, no timeouts or 500s, and final physical/reserved/available counters of 100/100/0. This demonstrates SQLite transaction correctness for this local scenario; it does not establish production throughput. I will also independently test simultaneous duplicate keys, rollback, CAS stock adjustments, tenant isolation, expiration, and restart persistence.
