# Sol: independent Stockade verification

I wrote `tests/adversarial.test.js` and `tests/contention.test.js` against the agreed HTTP and `createApp` contracts. Tests use in-memory or temporary SQLite files, never the demo database. The two-process test launches two independent `src/server.js` children against one new file and sends 500 checkout requests, alternating between servers. It also races the same checkout key through both servers, stops them, and reopens the file with a fresh process.

The first independent run passed five tests: multi-line rollback, tenant isolation and activity-trigger rollback, deterministic expiry and repeated state actions, restart persistence, and two-process contention. Reviewing the source then found a real session flaw: `sessions.created_at` was saved, but authentication only checked token existence. An artificially aged cookie still returned HTTP 200, causing the new regression to fail one of seven tests. Astra added a 24-hour server-side age check; the isolated regression passed afterward. I added stock-cap, refund-at-cap, payment-outcome conflict, and cancel-versus-payment checks, all of which passed. The injected activity trigger emits an expected `forced audit failure` log line while the HTTP operation fails and its writes roll back.

The final full independent run passed **8/8** tests. The measured two-process batch issued 500 unique one-unit checkouts against 100 units in **9,225 ms** on this laptop: **100 HTTP 201**, **400 HTTP 409**, no HTTP 500/503 or transport failures. The accepted orders had 100 distinct IDs. Final product counters were `onHand=100`, `reserved=100`, `available=0`. Simultaneous duplicate-key requests returned one 201 and one 200 for the same order; a fresh process could read and replay it. This is evidence for the stated local SQLite contention case, not a production throughput benchmark.

Other assertions cover current-state replay after refund, price snapshots calculated by the server, all-or-nothing multi-line reservation, rejection of price overrides, stale product-version conflicts, cross-tenant ID denial, expiry preventing late payment, paid orders surviving expiry, repeated ship/refund without double stock movement, clean failure when a refund would exceed the physical stock cap, and a single winning transition in a competing pay/cancel request. These checks do not model a remote payment provider: payment and refund are intentionally same-database simulations.
